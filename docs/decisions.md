# 設計の判断

選んだもの、理由、採用しなかった案を書く。「状態」が「案」のものは、まだ2人で合意していない。

## D1. 4つの部品と、その境界（状態：案、2026-11-05）

取得 → 台帳 → カレンダー → 面談画面 の4つに分ける。

- **取得（大学ごと）**：Chrome拡張の中で、大学ごとの部品が、ログイン済みの状態で全授業の課題を取り（YNUのように全授業をまとめた課題の一覧が無い製品では、授業ごとのページを順に読む）、決まった形の「観測」にしてサーバーへ送る。取りに行くきっかけはD7。観測は、授業、課題のIDかURL、題名、締切、提出の状態、取得した時刻、取得に失敗したかどうか。新規か変更かは判断しない。
- **台帳（共通）**：観測を前回と比べて、新規・延期・前倒し・取消・提出済みを決め、履歴に残す。大学ごとの最後に取得できた時刻を持ち、「取得が止まっている」と「課題がない」を分ける。
- **カレンダー（共通）**：学生のGoogleカレンダーの専用カレンダーに、公式の締切と準備の目安を別の予定として入れる。書き込むのはサーバーではなく拡張機能（D11）。変更があれば更新し、提出済みになったら通知を外す。
- **面談画面（共通）**：前回の面談からの変化、要確認、取得停止、前回の約束、次の一歩、通知の設定。

理由：大学ごとの違いを取得部品の中に閉じ込めれば、大学を増やすときは観測を出す部品を足すだけで済む。個人に合わせる部分（準備の目安を何日前に置くか、通知の時刻と回数）は台帳とカレンダーの設定に置く。観測の形を先に決めれば、YNUの部品（Sora）と京大の部品（orange）を別々に作れる。

採用しなかった案：本人が開いたページだけを読む方式（課題に気づかない学生はページを開かないため）。サーバーがLMSにログインする方式（認証情報を預かる危険と規約の問題）。

## D2. 言語はTypeScriptにそろえる（状態：案、2026-11-05）

拡張機能、Cloud RunのAPI、面談画面のすべて。データの形を `packages/core/` で共有でき（D14）、2人のエージェントが同じ書き方で作れる。

## D3. 開発用repoを別に置く（2026-11-05）

提出用repoはGitHub ActionsとPagesが使えず、公開されている。開発とCIは非公開の `shieikan/kadai-hisho` で行い、提出用へはmainを同じ履歴のままpushする。提出用repoの案内でも開発用repoを別に作ることが勧められている。

## D4. 通知はGoogleカレンダーの通知を使う（状態：案、2026-11-05）

通知の仕組みを自分たちで作らない。学生のスマホにはカレンダーの通知が既に届くので、予定の通知の時刻と回数を設定で決める。

## D5. 形の決まった画面は普通に解析し、Geminiは文章に使う（状態：案、2026-11-05）

課題の一覧のように形の決まった画面は、決まった手順で解析する。Gemini（Vertex AI、Gemini 3.8 Flash）は、お知らせやメールの文章から締切の変更を拾って台帳の課題にひも付けることと、面談の前に前回からの変化をまとめることに使う。形の決まった画面までGeminiに読ませると、確実さが下がり費用も増える。

## D6. 録音は、教員の許可を得た授業だけ。中核ができてから（2026-11-05、Sora）

録音から得た情報は、課題に添える文脈と、締切の食い違いの検出にだけ使い、台帳の締切は書き換えない。許可を得た授業には、誰から・いつ・どの範囲の許可かを記録する。

## D7. 取得は、本人がLMSを開いたときに走らせる（2026-11-05、Sora）

本人がふだん通りLMSにログインして、どのページでも開いたら、拡張機能が裏で全授業の課題を取りに行く。開いたページだけでなく、開いていない授業も含めて取る。毎日の自然なログインの中で走れば十分、という判断。

- 学生に求める操作は、ふだんのLMSへのログインだけ。ログインを促す通知は出さない。
- 大学ごとに「最後に取得できた時刻」を持ち、台帳と面談画面に出す。何日も取れていないことは、それ自体が支援担当にとっての情報になる（出すかどうかは共有範囲の設定で決める）。
- 京大のComfortable PandAも、PandAを開いたときに課題を取る方式で、同じ形になる。

採用しなかった案：
- 裏で定期的に取りに行き、ログインを保ち続ける方式。PCのスリープやブラウザの再起動で結局切れ、保つための仕組みが増える。
- 期限が切れたら自動で再ログインする方式。大学のIDとパスワードを預かることになり、MFAのコードを機械で読むとMFAの意味がなくなる。
- ログインが切れたら、本人にログインを促す通知を出す方式。継続して操作できない前提と合わない。

残る穴：LMSを何日も開かない週は、何も入ってこない。大学のメールに届く通知から取る入口は、中核ができてから考える。

## D8. 裏の取得は画面を邪魔せず、終わったら画面に反映する（状態：案、2026-11-05、Sora）

- **取得中に、本人が見ている画面を動かさない。** タブを開かない、ページを移動させない、入力を止めない。LMSへの取得は1件ずつ間を空けて行い、LMSにも負担をかけない。
- 取り方は2段構え。第一は拡張機能の裏（service worker）から取る。ログインの状態が付かずに取れなければ、開いているLMSのページの側（同じ origin）から、画面には何も足さずに取る。
- YNU LMSで確かめた結果（2026-11-05、試作 `spikes/ynu-session-probe`）：ログインの状態はURLのpathにある `;SID=...` で決まり、Cookieだけでは取れない。SIDを付ければ裏からでも取れた。そこで、ログイン後のページを content script が見つけたらSIDを裏の処理へ渡し、裏から取る。SIDは `chrome.storage.session`（ディスクに書かれず、ブラウザを閉じると消える）にだけ置き、サーバーへは送らない。ログに残すURLからもSIDを除く。
- **終わったら、変化があったときだけ知らせる。** 例：「新しい課題2件、締切の変更1件をカレンダーに入れました」。開いているLMSのページの隅に小さく出し、押すと学生の画面が開く。変化がなければ何も出さない。返事は求めない。
- 取得中は、拡張機能のアイコンに小さく印を出すだけにする。
- **手前の画面は再読み込みなしで変わる。** 学生の画面と面談画面は、Firestoreの変更をその場で受け取って書き換える。カレンダーは拡張機能が更新するので（D11）、Googleカレンダーのアプリにそのまま出る。

## D9. 大学ごとの部分を薄くする：共通の核、LMS製品ごとの定義、大学ごとの設定の3層（状態：案、2026-11-05、Sora）

| 層 | 中身 | 数 |
|---|---|---|
| 共通の核 | ログインを見つけたら取得を始める、1件ずつ間を空けて取る、失敗を記録する、HTMLから定義どおりに値を取る、日付を読む、観測を組み立てる。台帳・カレンダー・面談画面・支援の設定もここ | 1つ |
| LMS製品ごとの定義 | ログインの見つけ方（SIDの場所など）、授業一覧と課題一覧のページ、値のある場所。できるだけ宣言（データ）で書き、コードは書かない。APIのある製品（Sakai＝PandA）はAPIの型を1つ書く | 製品の数だけ（CoursePower、Sakai、manaba、Moodle、WebClass など） |
| 大学ごとの設定 | どの製品か、URL、表示名 | 数行 |

- 大学ではなくLMS製品ごとに作る。例えばCoursePower（富士通）はYNUのほか、青山学院大学や北見工業大学でも使われているので、定義を1つ作れば、ほかの大学は設定を足すだけで済む。
- 個人に合わせる部分（準備の目安、通知の時刻と回数、共有の範囲）は共通の核に置き、定義には入れない。
- 新しい製品に対応するときは、見本の画面を数枚Geminiに渡して定義の下書きを作らせ、見本で試験してから使う。実行時は定義どおりに読むので、毎回Geminiに読ませるより確実で費用もかからない。画面の作りが変わって読めなくなったら「取得失敗」として出し、Geminiで読み直した結果を確定にはしない。
- 定義は Node.js と見本のHTMLだけで書いて試験できるようにする。各大学の学生が、自分の大学の製品の定義を足せる（Comfortable PandAは学生有志が作った）。

採用しなかった案：大学ごとに取得部品をコードで書く（大学の数だけ同じようなコードが増える）。毎回Geminiに画面を読ませる（確実さと費用の面で劣る。D5）。

## D10. 技術の構成：広げるための仕組みはGoogleのサービスで持つ（状態：案、2026-11-05、Sora）

コードの置き方：TypeScriptのmonorepo。`packages/core`（共通の核。ブラウザのDOMに頼らず、拡張機能の裏・Node.jsの試験・サーバーのどこでも同じコードが動く）、`packages/extension`、`packages/server`、`packages/web`、`lms-definitions/`（製品ごとの定義と、試験用の見本）。Manifest V3の拡張機能の裏にはDOMParserがないので、HTMLの読み取りは純粋なJavaScriptのライブラリで行う（実装のときに選び、理由を足す）。

| 役目 | 使うもの | 理由 |
|---|---|---|
| サーバーを動かす | Cloud Run。ソースから直接デプロイし、コンテナはCloud Buildのbuildpacksに作らせる | Dockerfileを自分たちで持たなくてよい |
| 面談画面を配る | Firebase Hosting（必要ならApp Hosting） | 指定の実行基盤に入っている |
| 台帳と画面の即時反映 | Firestore | 変更をその場で画面に届けられる（D8） |
| ログイン | Firebase Authentication | 学生はGoogleアカウント、支援担当も同じ仕組みで入る |
| 手元での開発 | Firebase Local Emulator Suite（Firestore、Authentication、Hosting） | Docker Composeの代わりに、全体を手元で1つのコマンドで動かせる |
| **LMS製品の定義を配る** | Firestoreに置き、拡張機能が起動時に読む | 画面の作りが変わった、大学を足した、というときに、拡張機能を作り直してChromeウェブストアの審査を待たずに全員へ直せる。定義はデータでコードではないので、Manifest V3の「外から取ってきたコードを動かさない」決まりに触れない |
| 定義が壊れたことに気づく | Cloud Logging と Error Reporting | 取得部品が「読めなかった」ことを、個人の情報を除いて送る。LMSの画面が変わったら、利用者が気づく前に分かる |
| 定義の下書き | Vertex AIのGemini（D9） | 見本の画面から定義の下書きを作る |
| 秘密の情報 | Secret Manager | 秘密の値が要るときに、コードと分けて置く。GoogleのトークンとLMSの認証情報はサーバーに置かない（D11） |

今は作らないが、この形で広げられること：
- **大学ごとに分ける**：Identity Platformのマルチテナントで、大学ごとに支援担当の入口とデータを分ける。大学のシングルサインオン（学認などのSAML）での支援担当のログインもここでつなげる。
- **大学が自分で立てる**：支援に関わる情報を大学の外に出したくない場合に、大学のGoogle Cloudのプロジェクトへ同じ構成を立てる。手順はInfrastructure Manager（GoogleのTerraform実行サービス）にまとめられる。

採用しなかった案：Docker Composeでの手元の開発と、Dockerfileの手書き（同じことをGoogleのサービスでできる）。LMS製品の定義を拡張機能に埋め込んで配る（直すたびにストアの審査が要る）。

注記（Issue #71）：定義の配り方は設計案6節のAPI経由案とも異なり、今の実装では `lms-definitions/` のJSONを拡張機能とWeb画面に同梱する。FirestoreやAPIからの定義更新は未実装（[design.md](design.md) 6節）。上の表は当初の決定として残す。

## D11. 足した要件（2026-11-05、Sora）

| 要件 | 中身 | 理由 |
|---|---|---|
| 模擬LMS | 架空の授業と課題を載せた模擬LMSをFirebase Hostingに置く。試す人のための学生・支援担当のアカウントで、拡張機能を入れなくても、ブラウザだけで「先生が締切を延ばす → 学生がLMSを開く → カレンダーと面談画面が変わる」を試せる。CoursePowerとは違う作りにする | 拡張機能を入れずに一連の操作を試せるようにするため。定義を1つ足すだけで別の製品に対応できることも確かめられる |
| お知らせの文章（Gemini） | お知らせの文章から締切の変更を拾い、課題にひも付ける。課題の欄の締切は書き換えず、食い違いは「要確認」にする。架空のお知らせ30件ほどで、正しく拾えた割合を測る（PLAN.md の M3） | 延長や前倒しが、課題の欄ではなくお知らせの文章だけに書かれることがあるため |
| 効果の数字 | 実際の課題（手元だけで扱い、commitしない）を手で一覧にして正解とし、自動で拾えた件数・時刻・取りこぼしを比べる（M7）。支援担当への聞き取りで、面談での確認にかかる時間を聞く。統計は [background.md](background.md) | 効果を数字で示すため |
| 学生が見るもの | Googleカレンダーと、学生専用の画面（Webページ。Firebase Hostingに置き、スマホからも開ける）。拡張機能のポップアップに情報を詰め込まない（Sora、2026-11-05）。拡張機能は、LMSのページの隅に変化を1行で出し、そこから学生の画面を開けるようにするだけ | 見て決めるのに要るものだけを見せるため（D12） |
| カテゴリ | 教育 | — |
| ストア | 期間中はChromeウェブストアに出さない。試す人は模擬LMSで試す | ストアの審査がいつ終わるか分からないため |
| カレンダーの更新 | サーバーではなく拡張機能から、Chromeのログイン（`chrome.identity`）で行う。サーバーはGoogleの許可もLMSの認証情報も持たない | 利用者の許可をサーバーに預けないため。OAuthのテストモードでは、サーバーが持つ許可が7日で切れる |

遅れたときに削る順：①面談の前のまとめ ②PandA ③お知らせからの変更の検出。Geminiによる定義の下書き（D9）は、別の大学へ広げるときの入口になるので削らない（2026-11-06、Sora）。最後まで残すのは、YNUの取得、台帳、カレンダー、面談画面、模擬LMS、定義の下書き。

## D12. 見せる情報を絞って、認知の負荷を下げる（状態：案、2026-11-05、Sora）

台帳の中身（根拠、履歴、取得の記録）は仕組みのためのもので、利用者には見せない。見せるのは、その人が今それを見て何かを決められる情報だけにする。問題があるときだけ出す情報は、問題がないときは出さない。

| 誰が・どこで | いつも見せる | 問題があるときだけ見せる | 押したときだけ見せる | 見せない |
|---|---|---|---|---|
| 学生・カレンダー | 課題名と授業名、公式の締切、準備の予定、LMSの課題のページへのリンク | 予定名の「要確認」と、両方の日付（説明欄に1行） | — | — |
| 学生・取得のあと（LMSのページの隅） | 変化があったときの1行（例：新しい課題2件、締切の変更1件をカレンダーに入れました）。押すと学生の画面が開く | — | — | 変化がないときの知らせ |
| 学生・専用の画面 | 今週の締切、最近の変化 | 要確認 | 課題ごとの根拠（どこに何と書いてあったか）、最後に取得できた時刻 | 授業ごとの細目、履歴 |
| 学生・拡張機能のポップアップ | 学生の画面を開くボタンだけ | — | — | 課題の一覧 |
| 支援担当・面談画面 | 次の面談までの締切、前回の面談からの変化、前回の約束と次の一歩 | 要確認、何日も取得できていないこと | 課題ごとの履歴と根拠（どこに何と書いてあったか） | — |
| 誰にも見せない | — | — | — | 観測のID、取得の記録と所要時間、画面のHTML、SID、定義の版、Geminiの生の出力（試験と原因調査のためにログにだけ残す） |

言葉の決まり：責める言い方をしない。延長された課題に「期限切れ」を出さない。赤い警告は、本当に今日やらないと間に合わないものだけに使う。

見た目：先にフロンティアモデルに、架空のデータで画面の試作をHTMLで描かせ、それを見て決める。実装はその見た目に合わせる（Sora、2026-11-05）。画面を作る枠組みは試作を見てから選ぶ。学生の画面、面談画面、LMSのページの隅の知らせは、同じ色と文字の決まりにそろえる。Googleカレンダーの予定は、カレンダーの見た目のまま使う。

## D13. 画面の基準：学生は時間割、面談では空きコマに準備の時間を置く（2026-11-05、Sora）

画面の試作（`design/prototypes/2026-11-05/`）を3つのモデル（Fable・Astra・Argon）に同じ注文で作らせて比べ、次の形にした。

- **見た目と文言の基準**：`merged.html`。構成はFable、見た目（深い緑、明朝の見出しとゴシックの本文）はAstra、日本語の文言はArgonが書いた。文言だけを書き換えさせ、構成と日付が変わっていないことを機械で確かめた。
- **学生の画面**：時間割（曜日×時限）を主にする。各授業のマスに、その授業の次の締切を添える（`timetable-mocks-wide.html` の案A）。マスを押すと、その授業の課題が右に開く。PCの幅を主にし、狭い窓でも読めるようにする。
- **面談画面**：`merged.html` の面談画面に、時間割の空いたコマに準備の候補を置く欄を足す（案C）。候補をどのコマに入れるかは、面談で学生と支援担当が一緒に決める。決めたものだけが、学生の時間割とGoogleカレンダーに入る。学生に勝手に予定を押し付けない。
- **採用しなかった案**：2週間の帯と月のカレンダー（`calendar-views.html`）。帯は重なりがよく見えたが、Soraの想定は時間割の形だった。月の形はGoogleカレンダーと重なる。締切を日の列に置く案B（`timetable-mocks-wide.html`）は、行が増えると時間割が押されて読みにくくなる。

これで足りなくなるデータ：
- 授業の曜日と時限、各時限の時刻。YNU LMSのホームには曜日と時限で授業が並んでいるので、取得部品で取れる。時限の時刻は大学ごとの設定に置く（D9）。
- 準備の予定。どの課題の準備を、どの日のどの時限に置くか。面談画面で決めたときに作り、カレンダーの予定にもする。

## D14. 開発用の雛形（2026-11-05）

今回の雛形の依頼に沿って、Node 26・pnpm 11のworkspaceを `packages/*` に置く。D2の `shared/` に当たる場所は `packages/core/` とする。依存の版は各 `package.json`、実際の解決結果は `pnpm-lock.yaml` でそろえる。

| 対象 | 選択と理由 | 今は採用しない案 |
|---|---|---|
| 画面 | React + Vite。学生と面談の画面をコンポーネントに分け、Firebase Hostingへ静的な出力を置ける | Next.jsなどのSSR基盤（空画面には不要）。ルーター・UIライブラリ（2つの入口はpathの判定と普通のリンクで足りる） |
| 試験 | Vitest。TypeScriptを直接試験でき、拡張機能のChrome APIも置き換えられる | Jest（TypeScript向けの追加設定を増やさない） |

定義は [definition.json](../lms-definitions/coursepower/definition.json)、書式の型と検査は [definition.ts](../packages/core/src/definition.ts)。基本、ページの確認、授業の一覧、教材の一覧、課題の詳細、値の変換を持つ。未知のキーは入れ子も含めて拒否する。変換は引数付きの4種類（下記）、曜日・提出状態の対応表、1種類の日付書式に限る。正規表現やJavaScriptを自由に書く欄、HTTPメソッドやホストを指定する欄はない。大学のUTCオフセットは呼び出し側から渡す。

Issue #10で、製品固有の値を定義へ移した（2026-11-06、Codex。Issueの依頼に基づく変更）。`pattern` は次のいずれか1つ、または最大4つの配列とし、配列は前から順に適用する。途中で一致しなければ値を返さない。CoursePowerの授業IDは `call-argument` → `prefixed-id` の順に読む。

| 型 | 引数と読み方 |
|---|---|
| `prefixed-id` | `prefix` に続くASCII数字を文字列全体で確認し、ID全体を返す。接頭辞は英字から始まる英数字・`_`・`-`、1〜32文字 |

| `number-between` | NFKCで正規化した文字列の最初の `before` の直後にASCII数字と `after` があれば、数字を返す。題名には正規化しない |
| `call-argument` | `name` に一致する関数名、括弧、同じ引用符で囲まれた引数1つだけを読む。実行はしない。名前はJavaScriptのASCII識別子の文字で1〜64文字、引数は英数字・`_`・`-`で1〜128文字 |

`label`・`before`・`after` はUnicodeの文字・数字・句読記号・ASCII空白で1〜64文字とし、空白だけ、制御文字、URLは拒否する。引数を正規表現へ展開せず、文字列比較と固定した正規表現だけを使う。未知の型、余分なキー、配列の入れ子は拒否する。以前のパターン名は受け付けず、`readerVersion` を2、CoursePower定義の `version` を3に更新した。外部からの定義更新を扱う処理は今回追加していない。

## D26. 古い情報と取得の失敗を両方の画面で知らせる（2026-11-07、Issue #94）

- 決めた人：Sora（Issue #94）。判定を共通関数にまとめる実装はCodex。
- 採用：最後にLMSから取れた時刻から3日（72時間）以上たったとき、学生画面と面談画面の「① 確かめる」に同じ `notice` の帯を出す。取得が一部だけ成功した場合と失敗した場合も帯で知らせる。古さと失敗が重なった場合は、従来の学生画面と同じく古さの案内を優先する。
- 文言：学生画面は変えない。面談画面では「YNU LMS：最後にLMSから取ったのは11/4です。学生がLMSを開くと新しくなります。」の形で表示する。失敗時は「今回すべての課題を確認できませんでした。LMSを一緒に開いて確かめてください。」。新しい情報は従来の「◯◯ 時点の情報」を残す。
- 理由：古い情報のまま面談を進めることを防ぎ、学生と支援担当が同じタイミングでLMSを開く必要に気付けるようにする。
- 採らなかった案：学生画面だけに帯を出す案。支援担当が面談画面で古さを見落とすため。
