## D1. 4つの部品と、その境界（状態：決定、2026-11-05）

〔作品〕

注記：4つの分担は実装済み。取得・台帳・カレンダー・画面を通した確認はPLAN.mdのC43と[実機確認の記録](records/2026-11-07-c43-live.md)を参照。準備は自動の目安ではなく、D13・D25に沿って確定した予定を使う。通知はD30・D36も参照し、下の列挙を全項目の実装済み一覧とは扱わない。

取得 → 台帳 → カレンダー → 面談画面 の4つに分ける。

- **取得（大学ごと）**：Chrome拡張の中で、大学ごとの部品が、ログイン済みの状態で全授業の課題を取り（YNUのように全授業をまとめた課題の一覧が無い製品では、授業ごとのページを順に読む）、決まった形の「観測」にしてサーバーへ送る。取りに行くきっかけはD7。観測は、授業、課題のIDかURL、題名、締切、提出の状態、取得した時刻、取得に失敗したかどうか。新規か変更かは判断しない。
- **台帳（共通）**：観測を前回と比べて、新規・延期・前倒し・取消・提出済みを決め、履歴に残す。大学ごとの最後に取得できた時刻を持ち、「取得が止まっている」と「課題がない」を分ける。
- **カレンダー（共通）**：学生のGoogleカレンダーの専用カレンダーに、公式の締切と準備の目安を別の予定として入れる。書き込むのはサーバーではなく拡張機能（D11）。変更があれば更新し、提出済みになったら通知を外す。
- **面談画面（共通）**：前回の面談からの変化、要確認、取得停止、前回の約束、次の一歩、通知の設定。

理由：大学ごとの違いを取得部品の中に閉じ込めれば、大学を増やすときは観測を出す部品を足すだけで済む。個人に合わせる部分（準備の目安を何日前に置くか、通知の時刻と回数）は台帳とカレンダーの設定に置く。観測の形を先に決めれば、YNUの部品（Sora）と京大の部品（orange）を別々に作れる。

採用しなかった案：本人が開いたページだけを読む方式（課題に気づかない学生はページを開かないため）。サーバーがLMSにログインする方式（認証情報を預かる危険と規約の問題）。

## D7. 取得は、本人がLMSを開いたときに走らせる（2026-11-05、Sora）

〔作品〕

本人がふだん通りLMSにログインして、どのページでも開いたら、拡張機能が裏で全授業の課題を取りに行く。開いたページだけでなく、開いていない授業も含めて取る。毎日の自然なログインの中で走れば十分、という判断。

- 学生に求める操作は、ふだんのLMSへのログインだけ。ログインを促す通知は出さない。
- 大学ごとに「最後に取得できた時刻」を持ち、台帳と面談画面に出す。何日も取れていないことは、それ自体が支援担当にとっての情報になる（出すかどうかは共有範囲の設定で決める）。
- 京大のComfortable PandAも、PandAを開いたときに課題を取る方式で、同じ形になる。

採用しなかった案：
- 裏で定期的に取りに行き、ログインを保ち続ける方式。PCのスリープやブラウザの再起動で結局切れ、保つための仕組みが増える。
- 期限が切れたら自動で再ログインする方式。大学のIDとパスワードを預かることになり、MFAのコードを機械で読むとMFAの意味がなくなる。
- ログインが切れたら、本人にログインを促す通知を出す方式。継続して操作できない前提と合わない。

残る穴：LMSを何日も開かない週は、何も入ってこない。大学のメールに届く通知から取る入口は、中核ができてから考える。

## D8. 裏の取得は画面を邪魔せず、終わったら画面に反映する（状態：決定、2026-11-05、Sora）

〔作品〕

確認：PLAN.mdのC04・C05・C21に、裏の取得・ページ側への切替・変化の表示の証拠がある。状態を持つLMSで学生の操作を優先して中断・復帰する扱いは、後続のIssue #120と[統合実機確認](records/2026-11-07-integrated-live-verification.md)を参照。

- **取得中に、本人が見ている画面を動かさない。** タブを開かない、ページを移動させない、入力を止めない。LMSへの取得は1件ずつ間を空けて行い、LMSにも負担をかけない。
- 取り方は2段構え。第一は拡張機能の裏（service worker）から取る。ログインの状態が付かずに取れなければ、開いているLMSのページの側（同じ origin）から、画面には何も足さずに取る。
- YNU LMSで確かめた結果（2026-11-05、試作 `spikes/ynu-session-probe`）：ログインの状態はURLのpathにある `;SID=...` で決まり、Cookieだけでは取れない。SIDを付ければ裏からでも取れた。そこで、ログイン後のページを content script が見つけたらSIDを裏の処理へ渡し、裏から取る。SIDは `chrome.storage.session`（ディスクに書かれず、ブラウザを閉じると消える）にだけ置き、サーバーへは送らない。ログに残すURLからもSIDを除く。
- **終わったら、変化があったときだけ知らせる。** 例：「新しい課題2件、締切の変更1件をカレンダーに入れました」。開いているLMSのページの隅に小さく出し、押すと学生の画面が開く。変化がなければ何も出さない。返事は求めない。
- 取得中は、拡張機能のアイコンに小さく印を出すだけにする。
- **手前の画面は再読み込みなしで変わる。** 学生の画面と面談画面は、Firestoreの変更をその場で受け取って書き換える。カレンダーは拡張機能が更新するので（D11）、Googleカレンダーのアプリにそのまま出る。

## D9. 大学ごとの部分を薄くする：共通の核、LMS製品ごとの定義、大学ごとの設定の3層（状態：決定、2026-11-05、Sora）

〔作品〕

確認：共通の [definition.ts](../packages/core/src/definition.ts) と `lms-definitions/` の製品定義を分ける方針を採用済み。大学ごとの設定を数行足すだけで取得できる仕組み全体が完成したという意味ではなく、現在の拡張の [lms-request.ts](../packages/extension/src/lms-request.ts) はCoursePowerの定義を直接参照する。定義の下書きはC30、模擬LMSはC32の証拠を参照。PandAはC08・C09が未完了で、他大学での実機確認もしていない。

| 層 | 中身 | 数 |
|---|---|---|
| 共通の核 | ログインを見つけたら取得を始める、1件ずつ間を空けて取る、失敗を記録する、HTMLから定義どおりに値を取る、日付を読む、観測を組み立てる。台帳・カレンダー・面談画面・支援の設定もここ | 1つ |
| LMS製品ごとの定義 | ログインの見つけ方（SIDの場所など）、授業一覧と課題一覧のページ、値のある場所。できるだけ宣言（データ）で書き、コードは書かない。APIのある製品（Sakai＝PandA）はAPIの型を1つ書く | 製品の数だけ（CoursePower、Sakai、manaba、Moodle、WebClass など） |
| 大学ごとの設定 | どの製品か、URL、表示名 | 数行 |

- 大学ではなくLMS製品ごとに作る。例えばCoursePower（富士通）はYNUのほか、青山学院大学や北見工業大学でも使われているので、定義を1つ作れば、ほかの大学は設定を足すだけで済む。
- 個人に合わせる部分（準備の目安、通知の時刻と回数、共有の範囲）は共通の核に置き、定義には入れない。
- 新しい製品に対応するときは、見本の画面を数枚Geminiに渡して定義の下書きを作らせ、見本で試験してから使う。実行時は定義どおりに読むので、毎回Geminiに読ませるより確実で費用もかからない。画面の作りが変わって読めなくなったら「取得失敗」として出し、Geminiで読み直した結果を確定にはしない。
- 定義は Node.js と見本のHTMLだけで書いて試験できるようにする。各大学の学生が、自分の大学の製品の定義を足せる（Comfortable PandAは学生有志が作った）。

採用しなかった案：大学ごとに取得部品をコードで書く（大学の数だけ同じようなコードが増える）。毎回Geminiに画面を読ませる（確実さと費用の面で劣る。D5）。

## D10. 技術の構成：広げるための仕組みはGoogleのサービスで持つ（状態：決定、2026-11-05、Sora）

〔作品・進め方〕

注記：基本構成の実装・配備の証拠はC14・C26・C31・C35。HTMLのライブラリはD18で選んだ。下の表の定義配布は末尾のIssue #71の注記のとおり未実装で、定義の異常を利用者より先に検知するCloud Logging / Error Reportingの専用経路も実装されていない（[取得診断](../packages/extension/src/collection-diagnostics.ts)は拡張内）。Googleの認可をサーバーに置かない範囲は、D36では利用者の認可を指し、専用送信元の認可は別に扱う。

コードの置き方：TypeScriptのmonorepo。`packages/core`（共通の核。ブラウザのDOMに頼らず、拡張機能の裏・Node.jsの試験・サーバーのどこでも同じコードが動く）、`packages/extension`、`packages/server`、`packages/web`、`lms-definitions/`（製品ごとの定義と、試験用の見本）。Manifest V3の拡張機能の裏にはDOMParserがないので、HTMLの読み取りは純粋なJavaScriptのライブラリで行う（実装のときに選び、理由を足す）。

| 役目 | 使うもの | 理由 |
|---|---|---|
| サーバーを動かす | Cloud Run。ソースから直接デプロイし、コンテナはCloud Buildのbuildpacksに作らせる | Dockerfileを自分たちで持たなくてよい |
| 面談画面を配る | Firebase Hosting（必要ならApp Hosting） | 指定の実行基盤に入っている |
| 台帳と画面の即時反映 | Firestore | 変更をその場で画面に届けられる（D8） |
| ログイン | Firebase Authentication | 学生はGoogleアカウント、支援担当も同じ仕組みで入る |
| 手元での開発 | Firebase Local Emulator Suite（Firestore、Authentication、Hosting） | Docker Composeの代わりに、全体を手元で1つのコマンドで動かせる |
| **LMS製品の定義を配る** | Firestoreに置き、拡張機能が起動時に読む | 画面の作りが変わった、大学を足した、というときに、拡張機能を作り直してChromeウェブストアの審査を待たずに全員へ直せる。定義はデータでコードではないので、Manifest V3の「外から取ってきたコードを動かさない」決まりに触れない |
| 定義が壊れたことに気づく | Cloud Logging と Error Reporting | 取得部品が「読めなかった」ことを、個人の情報を除いて送る。LMSの画面が変わったら、利用者が気づく前に分かる |
| 定義の下書き | Vertex AIのGemini（D9） | 見本の画面から定義の下書きを作る |
| 秘密の情報 | Secret Manager | 秘密の値が要るときに、コードと分けて置く。GoogleのトークンとLMSの認証情報はサーバーに置かない（D11） |

今は作らないが、この形で広げられること：
- **大学ごとに分ける**：Identity Platformのマルチテナントで、大学ごとに支援担当の入口とデータを分ける。大学のシングルサインオン（学認などのSAML）での支援担当のログインもここでつなげる。
- **大学が自分で立てる**：支援に関わる情報を大学の外に出したくない場合に、大学のGoogle Cloudのプロジェクトへ同じ構成を立てる。手順はInfrastructure Manager（GoogleのTerraform実行サービス）にまとめられる。

採用しなかった案：Docker Composeでの手元の開発と、Dockerfileの手書き（同じことをGoogleのサービスでできる）。LMS製品の定義を拡張機能に埋め込んで配る（直すたびにストアの審査が要る）。

注記（Issue #71）：定義の配り方は設計案6節のAPI経由案とも異なり、今の実装では `lms-definitions/` のJSONを拡張機能とWeb画面に同梱する。FirestoreやAPIからの定義更新は未実装（[design.md](design.md) 6節）。上の表は当初の決定として残す。

## D11. 足した要件（2026-11-05、Sora）

〔作品・進め方〕

注記：D36でサーバーからのメール送信（A1）を決定した。「サーバーはGoogleの許可もLMSの認証情報も持たない」は、利用者のGoogle認可・LMSの認証情報について維持し、専用送信元のGmail認可だけを別に持つ。利用者のカレンダー更新は引き続き拡張が行う。削る順はD23で改めた。

| お知らせの文章（Gemini） | お知らせの文章から締切の変更を拾い、課題にひも付ける。課題の欄の締切は書き換えず、食い違いは「要確認」にする。架空のお知らせ30件ほどで、正しく拾えた割合を測る（PLAN.md の M3） | 延長や前倒しが、課題の欄ではなくお知らせの文章だけに書かれることがあるため |
| 効果の数字 | 実際の課題（手元だけで扱い、commitしない）を手で一覧にして正解とし、自動で拾えた件数・時刻・取りこぼしを比べる（M7）。支援担当への聞き取りで、面談での確認にかかる時間を聞く。統計は [background.md](background.md) | 効果を数字で示すため |

## D12. 見せる情報を絞って、認知の負荷を下げる（状態：決定、2026-11-05、Sora）

〔作品〕

注記：表示の基本方針はC18〜C23とD13・D26で具体化した。下の表は当初の整理であり、現在のポップアップには取得の状態も出す（[popup.ts](../packages/extension/src/popup.ts)）。「ログにだけ残す」はSID・実物のHTML・Geminiの生の出力をログへ残す許可ではない。SIDはD8・AGENTS.mdに従ってログに残さず、APIも本文やSDKの例外を返さない（[http.ts](../packages/server/src/http.ts)）。

台帳の中身（根拠、履歴、取得の記録）は仕組みのためのもので、利用者には見せない。見せるのは、その人が今それを見て何かを決められる情報だけにする。問題があるときだけ出す情報は、問題がないときは出さない。

| 誰が・どこで | いつも見せる | 問題があるときだけ見せる | 押したときだけ見せる | 見せない |
|---|---|---|---|---|

## D18. HTMLの読み取りに使うもの（2026-11-06）

〔作品〕

注記：下の読み取り範囲と未完了の記述は実装当初のもの。後続の取得・模擬LMS・定義の下書きの確認は、PLAN.mdのC04・C05・C30・C32を参照。

| 候補 | 判断 | 理由 |
|---|---|---|
| [linkedom](https://github.com/WebReflection/linkedom) | 採る | 公式にWeb・service worker向けの入口があり、CSSセレクタで入れ子の表や授業カードを読める。今回の4見本と、DOM・NodeのグローバルAPIがない隔離環境の試験に通った |
| [htmlparser2](https://github.com/fb55/htmlparser2)＋[css-select](https://github.com/fb55/css-select) | 今回は採らない | HTML解析とセレクタ検索を組み合わせられる代案。今回はlinkedomで要件を満たせたので、木の探索を別のAPIで組み立て直す理由がない |
| [cheerio](https://cheerio.js.org/docs/intro/) | 今回は採らない | jQuery風の探索APIを使えるが、今回は既存のDOMに近いAPIで足りる。worker向け入口のあるlinkedomを優先した。サイズの優劣は測っていない |
| [offscreen documentのDOMParser](https://developer.chrome.com/docs/extensions/reference/api/offscreen) | 採らない | 裏画面の作成とメッセージ通信が必要になり、Node.jsの試験と同じ実行経路にならない |

定義は [definition.json](../lms-definitions/coursepower/definition.json)、書式の型と検査は [definition.ts](../packages/core/src/definition.ts)。基本、ページの確認、授業の一覧、教材の一覧、課題の詳細、値の変換を持つ。未知のキーは入れ子も含めて拒否する。変換は引数付きの4種類（下記）、曜日・提出状態の対応表、1種類の日付書式に限る。正規表現やJavaScriptを自由に書く欄、HTTPメソッドやホストを指定する欄はない。大学のUTCオフセットは呼び出し側から渡す。

Issue #10で、製品固有の値を定義へ移した（2026-11-06、Codex。Issueの依頼に基づく変更）。`pattern` は次のいずれか1つ、または最大4つの配列とし、配列は前から順に適用する。途中で一致しなければ値を返さない。CoursePowerの授業IDは `call-argument` → `prefixed-id` の順に読む。

| 型 | 引数と読み方 |
|---|---|
| `prefixed-id` | `prefix` に続くASCII数字を文字列全体で確認し、ID全体を返す。接頭辞は英字から始まる英数字・`_`・`-`、1〜32文字 |
| `after-label` | `label`、空白、空でない題名の順に並ぶ文字列から題名を返す |
| `number-between` | NFKCで正規化した文字列の最初の `before` の直後にASCII数字と `after` があれば、数字を返す。題名には正規化しない |
| `call-argument` | `name` に一致する関数名、括弧、同じ引用符で囲まれた引数1つだけを読む。実行はしない。名前はJavaScriptのASCII識別子の文字で1〜64文字、引数は英数字・`_`・`-`で1〜128文字 |

`label`・`before`・`after` はUnicodeの文字・数字・句読記号・ASCII空白で1〜64文字とし、空白だけ、制御文字、URLは拒否する。引数を正規表現へ展開せず、文字列比較と固定した正規表現だけを使う。未知の型、余分なキー、配列の入れ子は拒否する。以前のパターン名は受け付けず、`readerVersion` を2、CoursePower定義の `version` を3に更新した。外部からの定義更新を扱う処理は今回追加していない。

採用しなかった案は、製品名付きのパターンを増やす方法（別製品のたびにコード変更が要る）と、定義に任意の正規表現を許す方法（入力から実行する式を組み立てるため）。依存は追加していない。[架空製品の定義](../lms-definitions/fictional/definition.json) と [試験](../packages/core/tests/parameterized-patterns.test.mjs) で、別の接頭辞・ラベル・区切り・関数名を読み取る。この定義は試験専用で、公開済みの模擬LMSやGeminiによる生成の証拠ではない（C30・C32は未完了）。

今回は保存HTMLからの中間結果まで。観測の型は変えていない。リンクは見本で除去済みのため、リンク・次ページは`null`のみを受け付ける。ログインの印、空一覧の印、一覧の終わりの印も根拠がないため未設定。0行を成功にせず、取得完了も出力しない。これらの設定と実際の取得処理はC04以降で確かめる。「未評価」から提出済みへの変換は、見本READMEの採取記録に基づく対応であり、別のCoursePower環境での意味は未確認。

M1は [見本README](../lms-definitions/coursepower/samples/README.md) の基準を使う。教材一覧9件と課題詳細1件の各3項目（題名・締切・提出状態）を比較する。締切は`dueText`と`dueAt`が両方一致したときだけ1項目の正解。重複する教材一覧は一度だけ数え、欠落を分母から除かない。一覧の公開期限は締切に置き換えず、正解どおり`null`として比較する。この割合は見本での一致率であり、実物での取得成功率ではない。全項目の比較は [html-reader.test.mjs](../packages/core/tests/html-reader.test.mjs)、worker向けバンドルの確認は [html-reader-worker.test.mjs](../packages/extension/tests/html-reader-worker.test.mjs)。お知らせ2見本はC02・C03の対象外で、今回の読み取りとM1には含めない。

- **選んだもの**：元の授業は接続先別に保存し、明示の対応をKULASISの授業文書に持つ。画面で合成し、名前・URL・課題キーはKULMS、曜日・時限はKULASISとする。契約は [data-shapes.md](data-shapes.md#kulasisの時間割と授業の対応issue-180)。
- **理由**：時間割だけの観測で課題を取消にせず、取得順によって別の情報源のURLや属性が消えないようにする。授業名の一致では別授業を区別できない。リンク先がsiteIdにならない場合は対応を作らない。
- **取得の経路**：時間割・授業サポートはcontent scriptの同一origin GET。KULMSへの科目リンクの解決だけは、[Chromeの公式資料](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)に従い、既存のKULMS host permissionを使うworkerのGETにする。content scriptは別originの制約を受けるため。要求は科目コードだけに限り、任意のURLや本文の代理取得を作らない。SSOのログイン操作やmeta refreshの追跡はしない。
- **比べた案**：授業文書を保存時に1つにする案は情報源の上書きと課題キーの変更を伴う。サーバーからLMSへ取得する案は認証情報を持たない境界に反する。HTML解析は導入済みのlinkedomを使い、新しいparserや依存は追加しない。
- **100件超**：現在の時間割との対応を優先し、未対応で残る締切のある授業を後に送る。それでも超えた授業には完読結果を作らない。未知の種別・公開状態は推測で除外しない。実物の値の確認と、別端末での対応キャッシュ共有は未実施。
- **実物の確認**：DOM・部局横断・科目リンクの最終URL・Cookieとセッション保持はorangeが [手順](records/2026-11-08-issue-180.md#orangeの確認手順152-c3に追加) で確かめる。デプロイや実物への接続はこの実装では行わない。

## D41. スマホのホーム画面からPWAを開く（2026-11-09、Issue #232）

〔作品〕

- **決めた人**：Sora（[Issue #232の決定](https://github.com/shieikan/kadai-hisho/issues/232#issuecomment-6728343149)）。依存を増やさずPWAにし、ホーム画面のアイコンから学生画面を開く。
- **理由と比べた案**：ネイティブアプリはストア配布が締切に間に合わず、アプリ内ブラウザではGoogleログインが拒否されるため認証の作り直しも要る。課題の取得はPCの拡張機能が続けて担当する。
- **実装の選択**：Codex。既存のロゴからアイコンを作り、manifestと小さなservice workerを追加する。[Workbox](https://developer.chrome.com/docs/workbox/)も同じ処理に使えるが、今回は依存を足さない決定と対象の小ささから採らない。保存するのは画面の殻と同じ配信元のハッシュ付きJS・CSSだけ。API・認証・外部通信は扱わず、オンラインでは毎回画面を再取得し、ビルドごとにキャッシュの版を自動で変える。
- **残る確認**：iPhone・Androidのホーム画面からの起動とGoogleログインは実機で確かめる。オフラインの殻を、課題の最新状態の保証や書き込み成功とは扱わない。確認の記録は [Issue #232](records/2026-11-09-issue-232.md)。

## D42. 学生本人が既存の共有を停止・再開する（2026-11-09、Issue #257）

- 決めた人：Sora（[Issue #257](https://github.com/shieikan/kadai-hisho/issues/257)と作業依頼）。学生が共有先を確認し、自分の判断で支援担当への共有を停止できるようにする。

- 比べた案：許可文書の削除は監査用の情報を失うため採らない。クライアントの直接書き込みは、本人確認と再送の判定をサーバーに集める既存方針に従って拒否する。
- Codexが範囲内で選んだこと：共用の組はUI・APIとも操作を拒否し、他の人の体験を止めない。個別の体験のやり直しでは、同じ組の支援担当の既存許可だけを再開する。一般の共有先の追加はこの画面に設けない。

## D43. 準備の保存を断る理由を固定コードで伝える（2026-11-10、Issue #260・PR #263）

Soraが別の準備予定との重複保存の拒否に合意し、断る理由を利用者に示すことを条件とした。作業依頼で授業・準備の重なり・過去・利用できない課題の区別を指定した。既存の `plan-conflict` にすべてまとめる案は、画面で理由を伝えられないため採らない。保存するデータの形は変えず、409の固定コードを区別する。重なった予定の課題名は応答に追加せず、固定コードだけを返す（Codexの実装判断。理由を示すために課題の情報を増やす必要がないため）。締切後・同じIDの食い違い・メール操作の現在の記録の返却は維持する。コードの正本は [data-shapes.md](data-shapes.md#準備予定の保存と取消issue-49)、画面の文は [ui-words.md](ui-words.md#準備の予定を断る理由issue-260)。
