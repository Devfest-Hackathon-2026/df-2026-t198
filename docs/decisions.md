# 設計の判断

選んだもの、理由、採用しなかった案を書く。「状態」が「案」のものは、まだ2人で合意していない。

## D1. 4つの部品と、その境界（状態：案、2026-11-05）

取得 → 台帳 → カレンダー → 面談画面 の4つに分ける。

- **取得（大学ごと）**：Chrome拡張の中で、大学ごとの部品が、ログイン済みの状態で全授業の課題の一覧を取り、決まった形の「観測」にしてサーバーへ送る。取りに行くきっかけはD7。観測は、授業、課題のIDかURL、題名、締切、提出の状態、取得した時刻、取得に失敗したかどうか。新規か変更かは判断しない。
- **台帳（共通）**：観測を前回と比べて、新規・延期・前倒し・取消・提出済みを決め、履歴に残す。大学ごとの最後に取得できた時刻を持ち、「取得が止まっている」と「課題がない」を分ける。
- **カレンダー（共通）**：学生のGoogleカレンダーの専用カレンダーに、公式の締切と準備の目安を別の予定として入れる。変更があれば更新し、提出済みになったら通知を外す。
- **面談画面（共通）**：前回の面談からの変化、要確認、取得停止、前回の約束、次の一歩、通知の設定。

理由：大学ごとの違いを取得部品の中に閉じ込めれば、大学を増やすときは観測を出す部品を足すだけで済む。個人に合わせる部分（準備の目安を何日前に置くか、通知の時刻と回数）は台帳とカレンダーの設定に置く。観測の形を先に決めれば、YNUの部品（Sora）と京大の部品（orange）を別々に作れる。

採用しなかった案：本人が開いたページだけを読む方式（課題に気づかない学生はページを開かないため）。サーバーがLMSにログインする方式（認証情報を預かる危険と規約の問題）。

## D2. 言語はTypeScriptにそろえる（状態：案、2026-11-05）

拡張機能、Cloud RunのAPI、面談画面のすべて。データの形を `shared/` で共有でき、2人のエージェントが同じ書き方で作れる。

## D3. 開発用repoを別に置く（2026-11-05）

提出用repoはGitHub ActionsとPagesが使えず、公開されている。開発とCIは非公開の `shieikan/kadai-hisho` で行い、提出用へはmainを同じ履歴のままpushする。提出用repoの案内でも開発用repoを別に作ることが勧められている。

## D4. 通知はGoogleカレンダーの通知を使う（状態：案、2026-11-05）

通知の仕組みを自分たちで作らない。学生のスマホにはカレンダーの通知が既に届くので、予定の通知の時刻と回数を設定で決める。

## D5. 形の決まった画面は普通に解析し、Geminiは文章に使う（状態：案、2026-11-05）

課題の一覧のように形の決まった画面は、決まった手順で解析する。Gemini（Vertex AI、Gemini 3.8 Flash）は、お知らせやメールの文章から締切の変更を拾って台帳の課題にひも付けることと、面談の前に前回からの変化をまとめることに使う。形の決まった画面までGeminiに読ませると、確実さが下がり費用も増える。

## D6. 録音は、教員の許可を得た授業だけ。中核ができてから（2026-11-05、Sora）

録音から得た情報は、課題に添える文脈と、締切の食い違いの検出にだけ使い、台帳の締切は書き換えない。許可を得た授業には、誰から・いつ・どの範囲の許可かを記録する。

## D7. 取得は、本人がLMSを開いたときに走らせる（2026-11-05、Sora）

本人がふだん通りLMSにログインして、どのページでも開いたら、拡張機能が裏で全授業の課題を取りに行く。開いたページだけでなく、開いていない授業も含めて取る。毎日の自然なログインの中で走れば十分、という判断。

- 学生に求める操作は、ふだんのLMSへのログインだけ。ログインを促す通知は出さない。
- 大学ごとに「最後に取得できた時刻」を持ち、台帳と面談画面に出す。何日も取れていないことは、それ自体が支援担当にとっての情報になる（出すかどうかは共有範囲の設定で決める）。
- 京大のComfortable PandAも、PandAを開いたときに課題を取る方式で、同じ形になる。

採用しなかった案：
- 裏で定期的に取りに行き、ログインを保ち続ける方式。PCのスリープやブラウザの再起動で結局切れ、保つための仕組みが増える。
- 期限が切れたら自動で再ログインする方式。大学のIDとパスワードを預かることになり、MFAのコードを機械で読むとMFAの意味がなくなる。
- ログインが切れたら、本人にログインを促す通知を出す方式。継続して操作できない前提と合わない。

残る穴：LMSを何日も開かない週は、何も入ってこない。大学のメールに届く通知から取る入口は、中核ができてから考える。

## D8. 裏の取得は画面を邪魔せず、終わったら画面に反映する（状態：案、2026-11-05、Sora）

（公開前に削除）

- **取得中に、本人が見ている画面を動かさない。** タブを開かない、ページを移動させない、入力を止めない。LMSへの取得は1件ずつ間を空けて行い、LMSにも負担をかけない。
- 取り方は2段構え。第一は拡張機能の裏（service worker）から取る。ログインの状態が付かずに取れなければ、開いているLMSのページの側（同じ origin）から、画面には何も足さずに取る。
- YNU LMSで確かめた結果（2026-11-05、試作 `spikes/ynu-session-probe`）：ログインの状態はURLのpathにある `;SID=...` で決まり、Cookieだけでは取れない。SIDを付ければ裏からでも取れた。そこで、ログイン後のページを content script が見つけたらSIDを裏の処理へ渡し、裏から取る。SIDは `chrome.storage.session`（ディスクに書かれず、ブラウザを閉じると消える）にだけ置き、サーバーへは送らない。ログに残すURLからもSIDを除く。
- **終わったら、変化があったときだけ知らせる。** 例：「新しい課題2件、締切の変更1件をカレンダーに入れました」。開いているLMSのページの隅に小さく出し、押すと一覧が開く。変化がなければ何も出さない。返事は求めない。
- 取得中は、拡張機能のアイコンに小さく印を出すだけにする。
- **手前の画面は再読み込みなしで変わる。** 面談画面と拡張機能の一覧は、Firestoreの変更をその場で受け取って書き換える。カレンダーはサーバーが更新するので、Googleカレンダーのアプリにそのまま出る。

## D9. 大学ごとの部分を薄くする：共通の核、LMS製品ごとの定義、大学ごとの設定の3層（状態：案、2026-11-05、Sora）

| 層 | 中身 | 数 |
|---|---|---|
| 共通の核 | ログインを見つけたら取得を始める、1件ずつ間を空けて取る、失敗を記録する、HTMLから定義どおりに値を取る、日付を読む、観測を組み立てる。台帳・カレンダー・面談画面・支援の設定もここ | 1つ |
| LMS製品ごとの定義 | ログインの見つけ方（SIDの場所など）、授業一覧と課題一覧のページ、値のある場所。できるだけ宣言（データ）で書き、コードは書かない。APIのある製品（Sakai＝PandA）はAPIの型を1つ書く | 製品の数だけ（CoursePower、Sakai、manaba、Moodle、WebClass など） |
| 大学ごとの設定 | どの製品か、URL、表示名 | 数行 |

- 大学ではなくLMS製品ごとに作る。例えばCoursePower（富士通）はYNUのほか、青山学院大学や北見工業大学でも使われているので、定義を1つ作れば、ほかの大学は設定を足すだけで済む。
- 個人に合わせる部分（準備の目安、通知の時刻と回数、共有の範囲）は共通の核に置き、定義には入れない。
- 新しい製品に対応するときは、見本の画面を数枚Geminiに渡して定義の下書きを作らせ、見本で試験してから使う。実行時は定義どおりに読むので、毎回Geminiに読ませるより確実で費用もかからない。画面の作りが変わって読めなくなったら「取得失敗」として出し、Geminiで読み直した結果を確定にはしない。
- 定義は Node.js と見本のHTMLだけで書いて試験できるようにする。各大学の学生が、自分の大学の製品の定義を足せる（Comfortable PandAは学生有志が作った）。

採用しなかった案：大学ごとに取得部品をコードで書く（大学の数だけ同じようなコードが増える）。毎回Geminiに画面を読ませる（確実さと費用の面で劣る。D5）。

## D10. 技術の構成：広げるための仕組みはGoogleのサービスで持つ（状態：案、2026-11-05、Sora）

コードの置き方：TypeScriptのmonorepo。`packages/core`（共通の核。ブラウザのDOMに頼らず、拡張機能の裏・Node.jsの試験・サーバーのどこでも同じコードが動く）、`packages/extension`、`packages/server`、`packages/web`、`lms-definitions/`（製品ごとの定義と、試験用の見本）。Manifest V3の拡張機能の裏にはDOMParserがないので、HTMLの読み取りは純粋なJavaScriptのライブラリで行う（実装のときに選び、理由を足す）。

| 役目 | 使うもの | 理由 |
|---|---|---|
| サーバーを動かす | Cloud Run。ソースから直接デプロイし、コンテナはCloud Buildのbuildpacksに作らせる | Dockerfileを自分たちで持たなくてよい |
| 面談画面を配る | Firebase Hosting（必要ならApp Hosting） | 指定の実行基盤に入っている |
| 台帳と画面の即時反映 | Firestore | 変更をその場で画面に届けられる（D8） |
| ログイン | Firebase Authentication | 学生はGoogleアカウント、支援担当も同じ仕組みで入る |
| 手元での開発 | Firebase Local Emulator Suite（Firestore、Authentication、Hosting） | Docker Composeの代わりに、全体を手元で1つのコマンドで動かせる |
| **LMS製品の定義を配る** | Firestoreに置き、拡張機能が起動時に読む | 画面の作りが変わった、大学を足した、というときに、拡張機能を作り直してChromeウェブストアの審査を待たずに全員へ直せる。定義はデータでコードではないので、Manifest V3の「外から取ってきたコードを動かさない」決まりに触れない |
| 定義が壊れたことに気づく | Cloud Logging と Error Reporting | 取得部品が「読めなかった」ことを、個人の情報を除いて送る。LMSの画面が変わったら、利用者が気づく前に分かる |
| 定義の下書き | Vertex AIのGemini（D9） | 見本の画面から定義の下書きを作る |
| 秘密の情報 | Secret Manager | Calendar APIの更新に使うトークンなどをコードと分ける |
| カレンダーの更新のやり直し | Cloud Tasks（余裕があれば） | Calendar APIが一時的に失敗しても、順番を保ってやり直せる |

今は作らないが、この形で広げられること：
- **大学ごとに分ける**：Identity Platformのマルチテナントで、大学ごとに支援担当の入口とデータを分ける。大学のシングルサインオン（学認などのSAML）での支援担当のログインもここでつなげる。
- **大学が自分で立てる**：支援に関わる情報を大学の外に出したくない場合に、大学のGoogle Cloudのプロジェクトへ同じ構成を立てる。手順はInfrastructure Manager（GoogleのTerraform実行サービス）にまとめられる。

採用しなかった案：Docker Composeでの手元の開発と、Dockerfileの手書き（同じことをGoogleのサービスでできる）。LMS製品の定義を拡張機能に埋め込んで配る（直すたびにストアの審査が要る）。

## D12. 見せる情報を絞って、認知の負荷を下げる（状態：案、2026-11-05、Sora）

台帳の中身（根拠、履歴、取得の記録）は仕組みのためのもので、利用者には見せない。見せるのは、その人が今それを見て何かを決められる情報だけにする。問題があるときだけ出す情報は、問題がないときは出さない。

| 誰が・どこで | いつも見せる | 問題があるときだけ見せる | 押したときだけ見せる | 見せない |
|---|---|---|---|---|
| 学生・カレンダー | 課題名と授業名、公式の締切、準備の予定、LMSの課題のページへのリンク | 予定名の「要確認」と、両方の日付（説明欄に1行） | — | — |
| 学生・取得のあと | 変化があったときの1行（例：新しい課題2件、締切の変更1件をカレンダーに入れました） | — | — | 変化がないときの知らせ |
| 学生・拡張機能の一覧 | 今週の締切（5件まで）、最近の変化（3件まで） | — | 最後に取得できた時刻（小さく） | 授業ごとの細目、履歴 |
| 支援担当・面談画面 | 次の面談までの締切、前回の面談からの変化、前回の約束と次の一歩 | 要確認、何日も取得できていないこと | 課題ごとの履歴と根拠（どこに何と書いてあったか） | — |
| 誰にも見せない | — | — | — | 観測のID、取得の記録と所要時間、画面のHTML、SID、定義の版、Geminiの生の出力（試験と原因調査のためにログにだけ残す） |

言葉の決まり：責める言い方をしない。延長された課題に「期限切れ」を出さない。赤い警告は、本当に今日やらないと間に合わないものだけに使う。

見た目：面談画面はAngularとAngular Material（Material 3）で作る。一から見た目を設計しなくても整った画面になり、Googleの技術でもある。拡張機能の一覧と知らせは、同じ色と文字の決まりに合わせる。
