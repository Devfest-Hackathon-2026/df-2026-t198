# 人が入らずに回す開発のループ（状態：案、2026-11-06）

2人とも5日間ずっと手が空いているわけではないので、人は方向と、まれな判断と、画面や言葉の好みだけを出し、残りはエージェントが回す。準備の段階（2026-11-04〜05）に決めた回し方を、今の構成（[PLAN.md](../PLAN.md)、CI、Discordから呼ぶClaude、2人のCodexのアカウント）に合わせて決め直したもの。使える仕組みや資源が増えたら、この文書の役と数字も見直す。

## 1. 流れ

```text
依頼（GitHubのIssue。Discordで受けた依頼もIssueにする）
  → 実行役が、Issueごとのbranchで作業する
  → 試験と指標を回し、点の低いところを直して、また回す
  → 実装と別の系統のエージェントが見直す
  → PRを出す（変更の前後の指標を書く）
  → 下の「mergeの条件」を満たせば、エージェントがmergeする
  → PLAN.md の条件を満たしたら [x] にする
  → 条件を満たしたとき・止まったときだけ、Discordに「報告の形」で書く
```

上がらなければ、推奨の案を付けて人に聞き、答えを待つ間は別のIssueを進める。

## 2. 数字

- 完成条件（PLAN.md のC番号）は試験で、指標（M1〜M7）は PLAN.md の「測り方」で確かめる。指標を1つのコマンドで出す仕組みは、まだ無い（最初に作る）。
- **点数のずるを防ぐ**：試験の正解（`lms-definitions/*/samples/*.expected.json` など）、判定の基準、指標の測り方を、それを通すための変更と同じPRで変えない。変えるときは別のPRにして、人の合意を取る。
- お知らせの見本（M3）のように数を測るものは、一部をエージェントに見せない確認用に分け、1日1回だけそれで測る。普段の値と大きくずれたら、見本に合わせすぎていることを疑う。
- Geminiに採点させるのは補助にとどめ、合否は機械の判定で決める。
- 画面の分かりやすさと言葉の自然さは、人が1日1回、5段階で点を付ける。その点も記録して、機械の数字と並べて見る。

## 3. エージェントが変えてよい範囲と、mergeの条件

| 範囲 | 扱い |
|---|---|
| 担当の機能の実装、試験の追加、Geminiへの指示文 | 変えてよい。条件を満たせばエージェントがmergeする |
| データの形、API、Firestoreの規則、画面の流れ、依存、技術 | 変更案を出し、人の合意を待つ（[AGENTS.md](../AGENTS.md)） |
| 試験の正解、判定の基準、指標の測り方 | 実装と同じPRで変えない（2節） |
| 秘密の情報、Google Cloudのリソースと課金、提出用repo | 触らない。要るときは人に確かめる |

mergeの条件。すべて満たしたときだけ、エージェントが `gh pr merge` で取り込む。

- CIが通る。
- どの指標も下がっていない。
- 上の表の1行目の範囲しか変えていない。
- 実装と別の系統のエージェントが見直した（Codexが書いたらClaudeが見る、その逆も）。
- 変更が数百行に収まる。

取り込んだものが気に入らなければ、消さずに取り消しのPR（revert）で戻す。エージェントがmergeしたPRにはラベル `auto:merged` を付け、後から一覧できるようにする。

## 4. 判断の重さで扱いを変える

| 重さ | 例 | エージェントの動き | 人への知らせ方 |
|---|---|---|---|
| 軽い | 範囲の中の実装の選び方、名前、試験の追加 | 自分で決め、理由をPRに書く | 知らせない |
| 中くらい | 画面の言葉、作業の順番、範囲の中での設計の選び方 | 推奨の案で先に進める。期限までに答えがなければ推奨の案で決める | Discordで知らせる |
| 重い | データの形、権限、外への公開、削除、課金、大会の決まりに関わること | そのIssueだけ止め、ほかは進める | Discordで2人に知らせる |

- 中くらいの判断の期限：日中（9〜22時）は2時間、夜は翌朝9時。答えが推奨の案と違ったときだけ直す。期限で決めたものは「自動で決めたこと」として報告に載せ、後から覆せるようにする。
- 人に出す質問は、中くらい以上で1日5件までにする。まとめて聞く。
- 質問の形：3行以内の状況、選択肢2〜3個、推奨の案、期限、答えなかったら何が起きるか。画面に関わるものはスクリーンショットを付ける。
- 答え方：Discordで番号を返す（Claude AgentがIssueに書き写す）か、Issueに番号をコメントする。

## 5. 止まって人に返すとき

- データの形、依存、技術を変える必要がある
- 相手の担当範囲（AGENTS.md）に触る必要がある
- 実際のLMSやGoogleのアカウントでの確認が要る
- 費用が増える
- 同じ数字が3周続けて上がらない
- 提出用repoに出す

## 7. Issueのラベル

| ラベル | 意味 |
|---|---|
| `auto:ready` | エージェントが拾ってよい |
| `auto:claimed` | 実行役が作業中（誰かをコメントに書く） |
| `needs:human` | 人の判断待ち。期限と、答えがないときに進む推奨の案を本文に書く |
| `auto:blocked` | 上限まで試して届かなかった。試したことと次の案を書く |
| `auto:merged` | エージェントがmergeした |
| `area:*` | 変えてよい範囲（例：`area:ynu`、`area:ledger`、`area:web`）。並べて進めるときに重なりを見る |

Issueの拾い方（実行役はどのアカウントでも同じ）：

1. `auto:ready` のうち、作業中の `area:*` と重ならない、いちばん古いIssueを選ぶ。
2. `auto:claimed` を付け、「誰が（例：`sora-codex-1`、`orange-codex`）・いつ始めたか」をコメントに書く。
3. コメントを読み直し、自分より先に別の実行役が拾っていたら、ラベルを戻して別のIssueへ移る（GitHubのラベルには同時に付けるのを防ぐ仕組みが無いため）。
4. 終わったら、`Closes #番号` を書いたPRを出す。
5. 3時間たっても進みが書かれない `auto:claimed` は、計画役が `auto:ready` に戻す。

## 8. Geminiの費用

- 費用は制約にならない。Geminiは1回の評価で数十円ほどの見込みで、（公開前に削除）。上限は、ループの暴走のような事故を防ぐためだけに置く。
- Vertex AI（有料。入力が学習に使われない）で、作品と同じ経路で呼ぶ。AI Studioの無料枠は使わない（入力がGoogleの製品の改善に使われ、回数の上限も画面でしか分からないため）。
- 1回の評価を実際に回してトークン数を測り、その後に上限を置く。1回あたりは測った値の3倍まで、1日の合計は3,000円まで。上限に当たったら止めてDiscordで知らせる。
- 実行役が、呼び出しの回数とトークン数から費用を見積もる。Google Cloudの予算の通知は遅れて届くので、止める役にはしない。

## 10. 理由を残す（テーマ「Own the Why」）

速く進むぶん、人が理由を説明できない部分が増える。人は、エージェントが決めたことを承認するためではなく、理由を理解するために読む。発表の質疑では、2人のどちらも、相手の担当の部分まで「なぜそうしたか」を説明できるようにする。

| 人が決める | エージェントが決める（人に聞かない） |
|---|---|
| 誰のどんな困りごとを解くか、何を作らないか | 技術の選定、設計、実装、試験、性能の改善 |
| 当事者・支援担当との関係、同意 | 範囲の中でのデータの持ち方、処理の分け方 |
| プライバシーとして許せる線（何を持たないか） | 指示文の調整（数字で決める） |
| 画面の言葉の手触り（エージェントが案を出し、人が点を付ける） | ライブラリ、構成、CIの組み方 |
| 順番と、範囲を削る判断。発表の物語と外への提出 | 失敗の調べと直し |

境界、依存、費用、大会の決まりに触れるときは、エージェントが決めたことでも2人の合意を取る（[AGENTS.md](../AGENTS.md)）。

迎合を防ぐ決まり：

1. 測れるものは測って決める。2案で迷ったら、両方を試験や指標にかけて、数字の良いほうを採る。
2. 人の技術の指示は、目的に直して受ける。「Xを使って」と言われたら、何を達成したいのかに言い換えてIssueに書く。より良い手段があれば、そちらを使って理由を書く。
3. 反対するときは一度だけ、根拠と代案を付けて言う。それでも人がそうすると決めたら従い、経緯を `decisions.md` に残す。
4. 人に聞くときは、推奨の案を先に書く。人の領域にかかる部分だけを聞く。
5. 人の案とエージェントの案が割れたとき、少しずつ混ぜた折衷にしない。どちらかを選ぶか、数字で決める。
6. 判定の基準を、後から人の好みに合わせて動かさない（2節）。
7. 前提が誤っていると判断したら、作る前に止めて、根拠と代案を返す。

記録の形：

- `decisions.md` の各項目に、候補、選んだもの、理由、採用しなかった案と、決めた人（人か、どのエージェントか）を書く。
- 系統の違うエージェントに同じことを考えさせて比べたときは、比べた結果（どちらの案を、なぜ採ったか）を `docs/records/` に日付つきで残す。
- 夜の報告に「今日エージェントが決めたことと、その理由」を3つまで入れる。2人がそれを読み、分からないものは反対ではなく説明を求める。
