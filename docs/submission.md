# 大会の決まりと提出物

大会（DevFest GDGoC Japan Hackathon 2026）の公式資料から、開発と提出に効く決まりだけを抜き出す。提出は東京の現地会場の条件に従う。

- 開発の決まりの確認日：2026-11-04（公式の参加者向け資料、運営の回答）。
- 提出の条件：2026-11-07公開の「提出物・提出ルール」と同日19:06の東京会場の告知（Issue #149の転記）を基にする。フォルダ名・拡張の配布・著作物利用シートは、2026-11-10の運営文書についてSoraが本作業で提示した内容を反映した。

## 説明資料の項目

| 区分 | 項目 |
|---|---|
| 冒頭 | 会場、チーム名、メンバー、アプリ名、カテゴリ、GitHubのURL |
| 必須 | 1. プロジェクトの概要／2. 解決する課題（対象の利用者、課題と根拠、既存の方法との違い）／3. Googleの技術の活用（実行基盤の選択と使った箇所、選んだ理由、良い点と悪い点）／4. アーキテクチャ図／5. プロジェクトをデプロイしたURL |
| 任意 | 6. 動作の確かめ方／7. アプリの詳細や機能の自由記述 |
| 採点の外だが必須 | 8. AIを使った場面・使い方・理由／9. 開発で得たもの・成長 |

- 任意の6には、審査する人が動作を確かめる手順と試す入力を書く（C33の試す人のアカウントと、C34の筋書き）。個人のパスワードやAPIキーは書かない。
- 「5. プロジェクトをデプロイしたURL」には、WebのURL `https://todoku.me` と、拡張のZIPを添付した提出用repoの [GitHub Releases](https://github.com/Devfest-Hackathon-2026/df-2026-t198/releases) のURLを書く。導入の一言として「ReleasesからZIPをダウンロードして展開し、Chromeの拡張機能の管理画面でデベロッパーモードを有効にして、展開したフォルダを読み込む」を添える。拡張と連携する学生画面の入口は [READMEの導入手順](../README.md#実際のlmsで使う場合) に従う。
- サンプルの例文を実績として流用しない。

## 提出の手順

1. 説明資料と著作物利用シートは指定テンプレート・様式をコピーし、スライドはGoogle Slidesで作る。3点を上の名前にし、MP4本体も同じGoogleドライブの提出フォルダに置く。フォルダ名は「[会場名]_[チーム名]」とし、今回は `Tokyo_orange` にする。ブラウザ拡張機能のZIPは提出用repoのGitHub Releasesに添付し、説明資料の項目5にWebとReleasesのURL・導入の一言を書く。
2. フォルダを「リンクを知っている全員が閲覧可」にし、ログインしていないブラウザで各資料と動画を開く。閲覧できない提出は審査されない。
3. 東京会場のGoogleフォームにGitHubのURLと提出フォルダのURLを出し、送信の控えを残す（C40）。締切の2026-11-10 19:00までは再送信でき、最新の送信が使われる。
4. 締切後は資料の追加・修正・差し替えをしない。閲覧権限の修正だけはできる。実行環境は次の決まりに従って凍結する。

## 締切後の実行環境（C41）

2026-11-10 19:00から11/14終了まで、次の決まりに従う。

| 扱い | 操作 |
|---|---|
| 禁止 | 再デプロイ、不具合の修正、プロンプト・モデル・機能に関わる設定の変更、手での復旧（再起動・認証の更新など） |
| 可 | 審査操作によるデータ更新、自動スケール、通常の定期処理、クレジットの補充 |

停止していても資料と動画で採点される。停止を理由に手で復旧しない。
