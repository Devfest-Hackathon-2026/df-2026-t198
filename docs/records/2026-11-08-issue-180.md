# Issue #180：KULASISの時間割とKULMSの対応

2026-11-08。架空のHTML・JSONとローカルのエミュレーターだけで確認。実物のLMSには接続していない。契約は [data-shapes.md](../data-shapes.md#kulasisの時間割と授業の対応issue-180)、理由は [D40](../decisions.md#d40-kulasisとkulmsを別に保存し明示の対応だけで時間割を補う2026-11-08issue-180)。

## 確認した操作

- KULASISのCP932見本から、月1・月3と火2を読む。前者の授業だけをKULMSのサイトに対応させ、名前が同じでも対応しない授業は別に残す。表の縦横の入れ替え・結合セルも試験する。読めない授業のあるコマは空きコマとして認定しない。
- 遅延ログアウトを追わず、即時refresh・ログイン画面・HTTPの認証遷移では失敗を送る。途中でログインが切れた回は時間割を送らない。学生の操作・移動は止めず、取得を中断する。
- 対応のある授業ではKULMSの課題・URL・キーを保ち、KULASISの曜日・時限を使う。学生画面ではコマを押して課題を開く。面談の時間割にも同じ課題を出す。未対応は時間割の外に出す。
- KULMSの101件で、最後のサイトが対応済みでも先に送る。残りは100件まで送り、送らない授業を固定の失敗に残す。302件でも失敗は200件以内に収める。未知の種別・公開状態は除外しない。課題の完読結果を送らなかった授業は、2回続けても取消にしない。
- 時間割を2回受領しても、KULMSの授業文書・課題文書・カレンダー予定の内容と更新時刻が変わらない。取得失敗では前の時間割を残し、完全な成功で見当たらなかったKULASIS授業だけを過去の扱いにする。
- 対応の優先用キャッシュは受領の成功後だけ保存。同じ本人・学期だけで利用し、変わった対応を使えるようKULMSの待ち時間を解除する。

## 通信と保存の境界

守る対象は本人の時間割・課題・認証情報と、課題の取消・予定の整合性。入力はLMSのHTML/JSONと拡張の内部メッセージで、LMSの生データは信用しない。

- content scriptからの別origin要求は、拡張自身のトップフレームのKULASISページに限定。科目コードだけを受け取り、固定したKULMSのGETにする。外部URL、別フレーム、別サイト、認証情報を含む行き先を試験で拒否する。返すのは検証したsiteIdだけ。本文・Cookie・認証URLは返さない。
- 時間割取得は同一origin、課題の取得も従来の同一origin。workerはFirebaseの本人を送信前・再送前に確かめる。対応キャッシュの本人・学期の分離と、失敗時の保持を試験した。
- サーバーの入力検査・情報源別キー・トランザクションを使い、別の情報源の文書へ書かない。授業の追加フィールドはKULASISだけで受け付ける。`kulasis-timetable` は課題・課題の完読結果を送れない。Firestoreの読み取り規則は既存の授業文書のものを使い、変更していない。
- 依存追加・課金・支払い・本番の権限や設定の変更は対象外。実Cookie・SameSite・SSO・別タブでのKULASIS利用者の切替は実物で未確認。1人・1接続先・1Chromeプロファイルの既存の前提を維持する。

## orangeの確認手順（#152 C3に追加）

前提：PRのレビューとmerge後、通常の設定でビルドした開発版の拡張を読み込み、学生画面と拡張を同じGoogleアカウントで連携する。実物のログインはorange本人が行う。公開や設定変更の手順はこの確認には含めない。

1. KULASISへ通常どおりログインして所属のページを開き、2秒操作を止める。学生画面のKULASISの更新時刻を確認し、現在の前期/後期の授業が正しい曜日・時限に出るかを実画面と照合する。複数コマ、表の縦横の切替、学部/研究科のパスも使う範囲で確かめる。
2. 授業サポートのKULMS科目リンクを本人のブラウザで開く。最終URLが `/portal/site/{siteId}` の形式になるかを確かめる。認証画面や別の形式なら、対応が取れなかった件数として記録する。siteId・科目コード・認証画面のURLをIssueへ貼らない。
3. 同じChromeプロファイルでKULMSを開き、2秒操作を止める。対応が取れた授業の課題がKULASISのコマに出るか、学生画面の授業ボタンから題名・締切・提出の状態とLMSリンクを確かめる。名前が同じだけの授業や対応のないサイトは、時間割の外に残るかを確かめる。
4. 面談の「② 相談する」も開き、同じ曜日・時限の授業名と次の課題、未対応の一覧を照合する。締切のカレンダーでは、KULMSの課題が同じ授業名・締切で1件だけ出て、KULASISを再取得しても予定が増えないかを確認する。課題の取消や書き換えを実物のLMSで起こさない。
5. サイトが100件を超える場合は、候補・送信・上限で送らなかった件数と固定の失敗コードだけを記録する。現在の時間割と結び付くサイトが優先されているかを確かめる。`type` と `published` の実際の形式が架空見本と異なるなら、実値の応答を貼らずに、未知の値として残ることを報告する。
6. KULASISの取得成功後10分以上待つか、拡張を再読み込みして、KULASISだけログアウトして開き直す。ログイン切れから取得を試せる場合に、前の時間割・KULMSの課題・カレンダー予定が消えないかを確認する。SSOの別originに移った画面ではcontent script自体が動かないため、失敗時刻が更新されたとは扱わない。通常のログインで回復できるかも確かめる。
7. 読み取り中の操作・移動が止まらないこと、時間を置いた再取得でセッションが持つことを別の回として確認する。記録は対象件数・一致件数・失敗コード・使った版だけ。実授業名・課題名・Cookie・トークン・生HTML/JSONは残さない。実物の画面が読み取れない場合は空の成功にせず、DOMの調査を別作業へ返す。
