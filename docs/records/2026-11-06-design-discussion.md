# 部品のつなぎ目の設計：ClaudeとAstraの話し合い（2026-11-06）

記録。書き換えない。結果は [design.md](../design.md)（PR #4、orangeの合意待ち）。

## 進め方

1. Claude（Claude Code）が、7つの論点に初案を書いた。
2. Astra（GPT-6-Astra、Codex）が、初案の誤り・抜け・もっと簡単な案を指摘した。仕様はGoogle・Chromeの公式の資料で確かめた（第1回）。
3. Claudeが、4日で作るために簡単にしたい点（A〜G）を返し、Astraが賛否と理由を返した（第2回）。
4. 合意した中身を、Argon（Gemini 4 Argon）が読み手（orange）向けの日本語に書き直した。項目名・URL・番号が変わっていないことを、Claudeが機械で確かめた。

## 第1回：Astraが初案を変えたところ

| Claudeの初案 | Astraの指摘 | 採ったもの |
|---|---|---|
| 観測への応答に、カレンダーへの操作の一覧を入れて返す | 応答を失うと操作も失う。面談画面で準備の予定を確定したときは観測が起きない | 予定の最終の形と版をFirestoreに保存し、拡張機能がそれに合わせる |
| 予定を作る前に、課題のキーで検索して二重を防ぐ | 2つの処理が同時に「無い」と判断できる | 予定IDを作る前に決めて保存し、再試行でも同じIDを使う（Googleの公式が勧める方法） |
| 共有の範囲を許可の文書に書けばよい | Firestoreの規則は、1つの文書の中の項目ごとには読み取りを制限できない | 共有の単位で文書を分ける |
| 準備の予定と共有の設定は、画面から直接書く | 保存とカレンダーの更新を一緒に確定する処理が別に要る | 画面はFirestoreを読むだけにし、書き込みはCloud RunのAPIに集める |
| 拡張機能から書けば、テストモードで許可が7日で切れる問題を避けられる | 公式の説明では、テストモードの認可そのものが7日で切れる | 理由を「サーバーがカレンダーの許可を預からないため」に直す（D11を直す） |
| 本文をFirestoreに保存しなければ、本文を残さないと言える | ログ、引用、Google側のキャッシュは別の条件 | 3つの条件を分けて確かめる |

ほかに、Astraが足したもの：一覧にあって詳細だけ読めなかった課題を取消の候補にしないこと、カレンダーのスコープを `calendar.app.created` にすること、`gemini-3.8-flash` は東京で提供されていないこと（あとでClaudeがAPIで確かめた）。

## 第2回：Claudeの簡単にする案への賛否

| Claudeの案 | Astraの判断 | 採ったもの |
|---|---|---|
| A. 共有を5つの区分から、一括と取消だけにする | 賛成 | 一括と取消だけ |
| B. 観測の順序を、PCの時計で決める | 反対。時計は補正で戻ることがある | 保存して1つずつ増やす番号で決める |
| C. 招待コードの試行回数の管理を省く | コードを128ビット以上にするなら賛成 | 128ビット以上の乱数にして省く |
| D. 模擬LMSのHTMLをCloud Runが作る | 賛成。ログインの経路、利用者の分離、キャッシュの指定を足す | 足したうえで採る |
| E. 定義を拡張機能に同梱し、APIで更新する | 賛成。直近に検査して採用した版も持つ | 同梱＋直近の版＋API |
| F. 実物のカレンダーに書くのは拡張機能だけ | 賛成。保存と反映を別の状態として出す | 採る |
| G. 全データの削除を後回しにする | 賛成。準備の段階の決め（P2）のうち全削除は対象外と書く | 採る |

## Claudeが決めたこと

- Bは、Astraの反対の理由（時計が戻る）が具体的だったので、Astraの案にした。
- A・C・E・Gは、4日で作る量を減らすため、Claudeの案にした。中核の要件（取消の誤り、同期の消失、共有の取消）を壊す経路が無いことを、Astraと確かめた。
