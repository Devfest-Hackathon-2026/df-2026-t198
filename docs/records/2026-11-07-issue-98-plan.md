# Issue #98 実装計画

- 目的：学生と共有中の支援担当が、LMSにない課題を追加し、登録者と締切を両方の画面で確かめ、許可された人が削除できるようにする。
- 前提：Issue #98のSoraの承認範囲。orangeの合意はmerge前に必要。デプロイ・merge・依存追加・OAuth scope追加は行わない。
- 保存：coreの`types.ts`に手入力専用の入力・保存型を追加。`manual-assignments` APIと`manualAssignments`コレクションを作り、serverの`plan-*`と同じ認証・トランザクション・再送・取消方式を使う。LMSの観測と台帳は変更しない。
- 権限：本人と有効な共有の支援担当が追加。本人は全件、支援担当は自分の登録分だけ削除。体験アカウントは自分の組だけ。直接書き込みは全員拒否。`security-review`ではこの境界・入力・再送・共有取消を検査する。新たな認証方式・秘密・依存・課金・デプロイ設定は対象外。
- 画面：`manual-assignments.tsx`のフォームと課題表示を学生・面談画面で共用。`student-data.ts`と`session-watch.ts`で購読し、授業の欄・締切順・次回面談までの一覧にLMS課題と並べる。日付のみを23:59へ補わない。登録者・任意の授業・短いメモを示す。
- 同期：coreの`calendar.ts`で締切予定を組み立て、既存の版付き同期対象を保存。体験用の保存済み予定と既存の拡張機能の実行役を利用する。実Googleへの書き込みは未確認として区別する。
- リセット：mainにある既存の本人専用リセットで手入力課題も消す。作業branchへmainを取り込み、既存機能を二重実装しない。PRは指定の`issue-49`ベースにする。
- 判断：大会までの運用で、土台だけではリセット操作が存在せず受入不能（観測済み）。mainの取り込みはF=10/S=4/C=4、リセットの複製はF=未確認/S=4/C=7（保守が二重になる）。前者を採用し、継承差分をPRに明示する。
- RED：まずAPIエミュレーターで本人・支援担当の追加と削除、他人の拒否を試験し、未実装の404を確認。規則試験では新コレクションの許可済み読み取りが失敗することを確認する。
- 検証：要求された6検査、手入力APIのAuth/Firestoreエミュレーター、規則、既存の準備予定、体験用カレンダー、ブラウザで追加→双方の画面→学生の削除→リセットを確認。1280px/390pxの写真を残し、M6を同じ8手順で測る。見本の正解と測定基準は変えない。
- 文書：`docs/data-shapes.md`に契約、`docs/decisions.md`にD27、確認後に記録とPLANの該当既存条件の証拠を追記。新たなC番号は作らない。
- 停止：承認外の依存・API・規則・LMS取得部品の変更が必要、実アカウント・課金・デプロイが必要、または前提が誤りと判明した場合はIssueに根拠と代案を残す。

## 検証中に判明した修正

- 既存のM6が、日本時間09:00前に「3日後」の架空締切を2日後として作る不具合を検出した。`systematic-debugging`の最小再現として00:00・03:30・08:59・09:00・23:59を単体試験にし、初期化と初期設定の生成処理を日本の日付で計算するよう直す。測定基準と見本の正解は変えない。
- mainとの接続で加わったリセットでは、PR #79の準備予定も同期待ちと一緒に消す。手入力だけを消して既存の準備予定が残る状態を避ける。新しいリセット操作は作らない。
- LMSだけの体験では従来どおりカレンダーを表示し、手入力の課題がある間は締切の近い一覧も表示する。M6の既存の表示条件を維持する。

## 停止判断

日付修正でM6は8/8に戻ったが、既存の`demo.emulator.test.ts:149`はUTCの日付で3日後を期待し、M6は日本の日付で3日後を期待していることが判明した。09:00 JST前は両者が1日ずれる。`docs/loop.md`の正解と実装を同じPRで変えない規則、および依頼の停止条件に従い、日付修正はrevertした。手入力の実装は残し、M6を未達としてdraft PRで渡す。基準の合意と修正は別PR、または現行の両基準が一致する09:00 JST以降の再測定が必要。
