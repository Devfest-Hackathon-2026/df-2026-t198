# Issue #40 実装計画

対象は学生の締切予定と、見直す担当者が確認する同期契約。根拠はIssue #40とdesign.md 5節。実カレンダーの確認はPRの手順をSoraが実施し、C15は残す。C16・C17は指定された偽API試験で判定する。

- coreのtypes.tsと新しいcalendar.ts：望ましい予定、版・世代、固定エラー、結果報告。公式締切を使い、本文は転記しない。
- serverのobservation-store.ts、新しいcalendar-store.ts・calendar-http.ts、http.ts・firebase.ts：台帳と同期対象を同じトランザクションで保存。本人認証、接続先の登録、未反映取得、版一致の結果報告。
- extensionの新しいcalendar-sync.ts・calendar-browser.ts、auth-probe-browser.ts、service-worker.ts、設定の型とbuild-config.mjs：既存の認証と専用カレンダーを使い、1実行役が順番に同期。送信成功後・worker起動時の入口。書き込み先は注入でき、模擬カレンダー自体は作らない。
- 対応するtests、docs/data-shapes.md、docs/decisions.md、PLAN.md：契約・判断・証拠のみ。依存、採点基準、既存見本は変更しない。

最初のRED試験は古い版の成功報告を拒否する境界。未実装の関数またはAPIの404で失敗することを確認してから実装する。偽Calendar APIで作成・変更・削除・応答喪失・再試行・提出・日付のみ・要確認を検証し、Auth/Firestoreエミュレーターで本人の分離とトランザクションを確認する。

最終検査は `pnpm typecheck && pnpm lint && pnpm test && pnpm build && pnpm progress --check && pnpm check:samples` と観測/同期のエミュレーター試験。PRは指定の5見出しで試験・未確認・実物確認手順を渡す。pushはissue-40だけ、mergeしない。

情報の境界：APIにはFirebase ID tokenだけを認証に使い、Googleのaccess tokenとSIDは渡さない。送信者が指定したuidでは保存先を選ばない。予定の本文は授業名・課題名・締切の原文・安全なリンク・食い違う日付のみ。支援担当には同期の内部文書を公開しない。追加依存・課金操作・提出用repo・実アカウントへの試験は対象外。合意済みの形を超える変更が必要なら停止する。
