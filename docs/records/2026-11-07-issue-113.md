# Issue #113：Gmailの通知と確認手順

PR #79 の `issue-49` 上の実装。#112の[応答の契約](https://github.com/shieikan/kadai-hisho/issues/112#issuecomment-6695451925)に合わせ、拡張内の `src/digest.ts` に消費側の型を置く。サーバー・画面との通し、Google Cloudの変更、実メールの受信は未確認。

## Soraがmerge後に行う操作

1. #112のAPIと画面が公開先へ反映されたことを確認する。拡張の `config.local.json` の `apiOrigin` と同じ接続先で使う。
2. Google Cloud Consoleで、既存の拡張用OAuthクライアントのプロジェクトを選ぶ。「APIとサービス」からGmail APIが有効か確認し、未設定なら有効にする。新しいプロジェクトやOAuthクライアントは作らない。
3. 「Google Auth Platform」→「データアクセス」→「スコープを追加または削除」で `https://www.googleapis.com/auth/gmail.send` を追加し保存する。既存のopenid・email・カレンダーのscopeは維持する。「対象」のテストユーザーに、Chrome・拡張・学生画面で使う本人のGoogleアカウントがあることも確認する。公開状態はテストモードのままにする。
4. `pnpm --filter extension build` の後、`chrome://extensions` で同じ拡張を再読み込みし、詳細から「拡張機能のオプション」を開く。Googleとの接続は既存の設定を使う。
5. 「毎朝、今日やることをGmailで受け取る」を入れる。この操作で初めてGmail送信の許可を求める。メールを読む許可や、他人への送信は不要。Google画面の本人のアカウントと、送信の許可を確認する。
6. 当日の内容があり、7:30を過ぎていれば、その日の朝の分をすぐ送る。本人のGmailの受信トレイと送信済みで、送り元・宛先が本人だけか、件名・日本語本文・LMSのリンク・「終わった」「後回し」のリンクを確認する。本文が0件なら送らない。受領・ボタンの結果は実物で確かめた後に別の記録へ残す。
7. 許可が切れた場合は切り替えを一度切って、入れ直す。通常の接続テストはカレンダー用のscopeだけを求めるため、Gmailの再許可にはこの切り替えを使う。OFF後は新しいメールを送らない。既に送信処理へ渡ったメールを取り消す機能ではない。

## 送信の条件と限界

- 日本時間7:30のアラームと毎分の確認。起動時にアラームを復元し、その日の朝の分だけ補う。準備の追加・移動・取消はAPIの最新の応答で確認し、開始30分前から開始時刻までの間に1回だけ送る。ChromeやPCが停止している間の定刻の到着は保証しない。
- #112の朝の本文と、予定ごとの短い本文を変更せずにUTF-8のメールへ入れる。`empty: true` では送らない。GoogleとFirebaseが同じ本人で、応答の宛先もFirebaseのメールに一致するときだけ送る。返信先・CC・BCCは付けない。
- 設定は本人・Firebaseプロジェクト・OAuthクライアントに結び付ける。送信記録の値は日本時間の日付と予定IDの配列だけ。朝の分は予約済みID `morning` で表し、次の日には前日の配列を置き換える。メール本文・課題・トークンは保存しない。
- 送信直前に記録するため、Gmailが受理した直後の応答喪失やworker停止でも同じ通知を再送しない。その代わり、記録後・送信前の停止やHTTP失敗では未着になり得る。送信を確認できない場合は設定画面に案内を残す。切り替えを入れ直しても同日の送信記録は消さない。
- 秘密情報の検査は、観測送信と同様の識別子・URLエンコードに加え、HTMLエンコードと手元の現在のSID・認証トークンの一致を拒否する。未知の秘密が任意の文章に紛れている場合を完全に識別するものではない。入力は#112が返す題名・締切・リンクだけという前提。

## 検証

- `tests/digest.test.ts`：JSTの境界、UTF-8の件名と2種類の本文、本人だけの宛先、ヘッダー差し込み、秘密情報の拒否。
- `tests/digest-browser.test.mjs`：偽のdigest/Gmailで7:30・遅い起動・worker再開・予定30分前・重複・OFF・empty・別人・認可失効・scope拒否・送信応答喪失。許可画面を開いている間のOFFが勝つことも確認。
- `tests/auth-probe-browser.test.mjs`・`tests/calendar-browser.test.mjs`：既存の認証が元のscopeだけを明示し、Gmailの許可を求めないことを確認。`tests/probe-build.test.mjs`：生成したmanifestのscope・alarms・Gmailの接続先を確認。
- `tests/digest-options.browser.mjs`：Chromiumで初期OFF、ON/OFF、許可拒否、通信失敗、秘密を含む例外の非表示、横はみ出しなし。画像は[1280px](2026-11-07-issue-113/options-wide.png)・[390px](2026-11-07-issue-113/options-narrow.png)。
- 指定の6検査の最終結果はPR本文に記載する。PLAN.mdに新しく満たすC番号はなく、チェックは変更しない。M1〜M7は取得・台帳・カレンダー等の指標で、今回のGmail送信の比較指標は定義されていないため対象外。

検証は架空のデータだけを使用。実LMS・実課題・Googleの認証情報を読み出さず、Gmail・Google Cloudの操作は行っていない。新規の依存・外部素材はない。脅威面は本人への送信権限・設定操作元・本文の秘密・重複送信であり、偽APIで確認した。課金、データベースの規則、外部コードの取り込みは変更していない。
