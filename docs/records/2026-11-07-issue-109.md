# Issue #109：LMS操作中の取得の再試行

対象：Issue #109の最新本文と、学生自身の画面にはエラーが出なかったという追加コメント。実機の原因は未確認。

## 確かめたこと

- サーバーが発行したフォーム値を、取得途中の学生の画面移動で無効にする偽LMSを作った。既存の架空HTML・正解は変更していない。修正前は、古い値へのHTTP失敗と、HTTP 200で別種類のページが返る場合の授業・詳細の4試験で全授業を読めなかった。
- 修正後は、3件目の授業／詳細の要求直前に画面移動を入れた4試験で、22授業・132課題を取得。実際のworker、取得・読み取り処理、ページ側への切替を通す試験も成功した。実物のCoursePowerが同じ状態管理をすることの証明ではない。
- 授業はホームを開き直して1回だけ再試行する。詳細は一覧を開き直して1回だけ再試行する。その一覧の再取得にもホームの更新が必要なら、授業ごとの1回の再試行枠を共用する。ログイン切れを確認したら再試行・経路切替をせず、残りの取得も止める。
- ページ側では授業全体の取得が3件連続で失敗したら残りの通信を止める。間に成功した授業があれば連続数を戻す。偽LMSの継続失敗では3授業分の6回の授業要求と4回のホーム要求だけが通信した。経路の成功カウンターは従来どおり取得1回ごとに数える。
- 有効な観測の受領結果を確認した時刻をsessionに保存し、その後10分は取得・認証・アイコン更新をしない。一部取得の観測を送れた場合も待つ。送信前のログイン・設定不足、送信失敗、不正な受領結果では待たない。workerの再起動と10分の境界、送信に時間がかかった場合を試験した。

## 診断と境界

`ynuFetchSummary` の追加項目は `firstFailure` と `recovered`。前者は `stage`（home/course/detail）、`route`（background/page）、`httpStatus`（不明はnull）、`pageType`（定義の3種類、不明はunknown）、`path`（不明はnull）のみ。後者は授業・詳細それぞれの再試行で回復した件数なので、詳細と親の授業がともに回復すれば2件。

パスはSIDなどのmatrix parameter・query・fragmentを除き、既知の移動先だけを許可する。未知のパスはIDを含み得るため残さない。ID・名前・フォーム値・HTML・秘密値を要約に残さない試験を通した。診断はsession内だけで、観測APIの形は変えていない。提出・認証の権限、依存、公開終了・学期の扱い、250msの待機と既存の要求タイムアウトは変更していない。

## 残る確認

C04は未完了のまま。merge・拡張の更新後にSoraが、取得中に授業を開く／ホームに戻る操作をしても `ynuFetchStatus: 'success'` になることを確かめる。失敗したら件数と上記の診断だけを共有し、秘密値や観測本文は貼らない。再試行の直後にも学生が画面を移る場合は、上限の1回で回復できない可能性が残る。別の原因候補は、タブの移動によるページ側の受信先documentの終了、LMS側の一時的な拒否やタイムアウト。今回は実機での識別とデプロイを行っていない。
