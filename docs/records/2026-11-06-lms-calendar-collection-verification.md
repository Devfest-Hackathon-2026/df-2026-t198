# LMS取得後のカレンダー同期の確認

2026-11-06、基点main `bd47aa7`。LMS観測の受領検証後に既存の同期関数を起動する。同期の完了を待たず、LMSへの応答と取得状態の保存を先に進める。

## 実測

未接続版に新しいworker通し試験を加えると、取得後の同期とCalendar失敗の報告の2件が失敗した。受領後に同期をawaitする版は、その2件を通したが、Calendar GETが未解決の試験で観測結果と取得状態が返らなかった。非同期起動に変えると4件すべて成功した。

管理対象worktreeで、拡張の全100件と型・lint・buildが成功。さらにrepo所定の6検査（`pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build`、`pnpm progress --check`、`pnpm check:samples`）がすべて終了コード0。Firestore規則38件もエミュレーターで成功した。通常試験のエミュレーター専用27件はskipであり、実行済みとは扱わない。見本17ファイルが成功し、手元の実資料との比較は資料がないため省略した。Webの既存の大きなchunk警告は残る。

## 見直しへの対応

別系統のClaude Codeの見直しでも、awaitによる通知・ロック解除・状態保存の遅延を指摘された。未解決GETの失敗を実測した上で、同期を待たない形へ直した。拒否時の試験は、観測送信後にcalendar-sync要求が無いことも直接確認する。取得単体試験には同期のモックを明示し、不完全な認証モック内の例外で通っていた経路を分離した。

## 境界と残件

本人の確認、専用カレンダーIDの限定、予定の所有マーカー照合は既存関数を利用する。API、型、依存、権限、認証方法を変更していない。

すでに走っている起動時の同期が最後の未処理一覧を読む直前・直後に観測が受理される場合、または起動時の同期が途中で失敗した場合、新しく受理した予定は次の同期のきっかけまで遅れる可能性がある。既存の実行中Promiseの共用によるもので、今回新しい再試行基盤は足さない。実機で継続的な取りこぼしが確認された場合に別途扱う。
