# 開発の仕組みの見直し：FableとAstra（2026-11-06）

記録。書き換えない。決めたことは [decisions.md](../decisions.md) のD21。

## 進め方

Soraの依頼で、Claudeが作った開発の仕組み（orchestrator、Codexへの割り振り、mergeの関所、Discord、PLAN.md）が目的に沿っているかを、Fable（Claude Fable、思考の深さmax）とAstra（GPT-6-Astra、max）に、同じ頼む文で独立に見直させた。まれな条件の抜けは、目的を損なわない限り見なくてよい、とした。目的は、作品を完成させて提出する、完成条件を締切までに満たす、人がコードを読まずにループが回る、資源を活かす、公開してはいけないものを出さない、の5つ。

## 2つが一致した指摘

| 指摘 | 中身 |
|---|---|
| 拡張機能を入れずに試す人の経路が最後にある | 模擬LMSからデプロイまでが未着手で、日程の最後に置かれていた |
| 提出物が計画の外にある | 説明資料・デモ動画・著作物利用シート・Googleドライブのフォルダに、条件も担当も無かった |
| ループが人なしで回る条件が無い | 拾えるIssueが1件だけ。次の作業のほとんどが人の印の要るファイルに触る |
| Claudeに集中している | 割り振り・見直し・commit・PR・mergeが全部Claudeを通る |
| 公開の点検 | 古いcommitに、公開してはいけない文がある。同じ履歴のまま送る決まりと両立しない |
| 担当が決まっていない | 残りの条件の多くが担当未定 |

## どちらか一方だけの指摘

- Fable：Discordの会話が、orchestratorと同じ作業ツリーで書き換えとgitをできる。見直しのたびに全試験を回し直すのはCIと重なる。設計が重い（観測の通し番号、招待コード、人ごとの模擬LMSのHTML）。削る順で、お知らせの読み取り（C28）が早く落ちる位置にある。
- Astra：Own the Why は、記録を増やすより、2人が主な選択を短く説明できるかを確かめる形で十分。

## 割れたところ

画像で画面の案を作る工程を、Fableは「HTMLの試作があるのでやめてよい」、Astraは「代表の画面で1回だけ選ぶ」とした。Soraの判断で、Astraの案（学生の時間割と面談画面の2つ）を採った。

## 採ったものと採らなかったもの

採ったものは D21。orchestratorをFableにするかはSoraが考え、費用の面から、orchestratorはClaudeのまま、Fableは朝夜の見直しに使うことにした。
